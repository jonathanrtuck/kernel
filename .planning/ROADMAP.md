# Roadmap: Kernel Verification

## Overview

Five phases of systematic verification, ordered by confidence gained per effort
invested. Phase 1 installs property-based testing across the highest-value
invariants. Phase 2 audits every unsafe block in frame/ for correctness. Phase 3
measures coverage and writes targeted tests for blind spots. Phase 4 builds a
bare-metal syscall fuzzer and confirms the kernel holds under random operation
sequences. Phase 5 models concurrency protocols under all thread interleavings
using Loom. When all five phases are complete, every kernel invariant is covered
by at least one technique capable of finding bugs the developer didn't
anticipate.

## Phase Details

### Phase 1: Property Testing

**Goal**: Core kernel invariants are verified by property-based tests that
explore input spaces no developer-written test would cover **Depends on**:
Nothing (first phase) **Requirements**: PROP-01, PROP-02, PROP-03, PROP-04,
PROP-05, PROP-06 **Success Criteria** (what must be TRUE):

1. `cargo test` runs proptest cases for capability encoding, arena allocation,
   rights bitmasks, slot arithmetic, and scheduler properties without any
   failures
2. A capability encoded and decoded roundtrips to the original
   ObjectType/Rights/badge for any valid input generated by proptest
3. Arena allocation tests confirm no double-alloc, no ID overlap, and freed
   slots are reusable across any sequence proptest generates
4. Rights bitmask operations (union, intersection, subset, attenuation) satisfy
   all algebraic laws under proptest
5. `scripts/verify` passes with proptest cases included in the test run
   **Plans:** 3/3 plans complete Plans:

- [x] 01-02-PLAN.md — Arena proptest: alloc/free sequence invariants

      consistency

### Phase 2: Unsafe Audit

**Goal**: Every unsafe block in frame/ has a verified SAFETY comment, aliasing
is clean, asm options are justified, and findings are documented per-file
**Depends on**: Phase 1 **Requirements**: SAFE-01, SAFE-02, SAFE-03, SAFE-04,
SAFE-05, SAFE-06 **Success Criteria** (what must be TRUE):

1. Zero unsafe blocks in frame/ lack a SAFETY comment (the ~37-block gap is
   closed)
2. Every SAFETY comment's stated precondition is confirmed against all call
   sites — no comment asserts a condition callers don't actually uphold
3. No reachable aliasing violation exists: mutable references and pointer casts
   in unsafe code are confirmed sound
4. Every inline asm `options()` annotation is justified against the ARM
   Architecture Reference Manual — any unjustified `nomem` is removed or
   replaced
5. Speculation barriers are present for all user-provided index dereferences in
   frame/
6. A per-file audit record exists documenting status (clean / fixed /
   known-risk) for every file in frame/ **Plans:** 4 plans Plans:

- [x] 02-01-PLAN.md — Audit cores.rs + fields.rs (hot-path dispatch, 127 unsafe
      blocks)
- [x] 02-02-PLAN.md — Audit mapping.rs + mmu.rs + boot.rs + slab.rs (memory
      subsystem)
- [x] 02-03-PLAN.md — Audit lock.rs + capabilities.rs + mod.rs + exception.rs +
      arch files (infrastructure)
- [ ] 02-04-PLAN.md — Per-file audit report document (SAFE-06)

### Phase 3: Coverage

**Goal**: Coverage is measurable on demand, every source file with critical
paths below 50% is identified, and targeted tests bring uncovered paths above
80% **Depends on**: Phase 2 **Requirements**: COV-01, COV-02, COV-03, COV-04
**Success Criteria** (what must be TRUE):

1. Running `scripts/coverage` (or equivalent) produces per-file line and branch
   coverage reports without manual steps
2. A complete list of source files with line coverage below 50% exists and is
   reviewed
3. Targeted tests are written for every critical uncovered path identified in
   the above list, bringing those paths above 80% line coverage
4. Coverage tooling is integrated so it can be run alongside or as part of
   `scripts/verify` **Plans**: TBD

### Phase 4: Fuzzing

**Goal**: A bare-metal syscall fuzzer runs random valid operation sequences and
the kernel survives all of them without panic or hang **Depends on**: Phase 3
**Requirements**: FUZZ-01, FUZZ-02, FUZZ-03, FUZZ-04, FUZZ-05, FUZZ-06 **Success
Criteria** (what must be TRUE):

1. A bare-metal test exists that generates and executes random valid syscall
   sequences under the hypervisor without manual intervention
2. The fuzzer exercises capability operations (Create, Mint, Clone, Destroy,
   Close) with random but valid inputs
3. The fuzzer exercises IPC operations (Call, Send, Receive) with random
   payloads
4. The fuzzer exercises memory operations (Space mapping, Field split/transfer)
   with random parameters
5. A multi-hour fuzzing run completes with no kernel panics, hangs, or assertion
   failures
6. A specific seed value reproduces any fuzzer run exactly, enabling regression
   testing of discovered sequences **Plans**: TBD

### Phase 5: Concurrency Modeling

**Goal**: IPC rendezvous, lock-free structures, scheduler queues, and Observer
lifecycle are verified correct under all interleavings Loom can explore
**Depends on**: Phase 4 **Requirements**: CONC-01, CONC-02, CONC-03, CONC-04,
CONC-05 **Success Criteria** (what must be TRUE):

1. A Loom model of the IPC rendezvous protocol exhausts all sender/receiver
   interleavings and finds no data races or deadlocks
2. Lock-free data structures in frame/ are modeled in Loom and confirmed
   linearizable under concurrent access
3. Scheduler queue enqueue/dequeue under concurrent load is verified in Loom
   with no lost or duplicated entries
4. Observer lifecycle transitions (create/suspend/resume/destroy) are verified
   in Loom under concurrent access with no use-after-free or invalid state
   transitions
5. All Loom models run as host-side `#[test]` functions reachable via
   `cargo test` **Plans**: TBD
