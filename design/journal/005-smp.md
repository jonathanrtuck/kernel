# SMP Exploration — 2026-04-10

Fifth exploration. First Level 2 question: how does the kernel operate on
multiple cores? Research document: `design/research/smp.md`.

## Starting point

From spec.md, the open question: "Multiple concurrent reactors, Context model
synchronization." Journal 003 flagged it: "SMP means multiple reactors
concurrently updating the model. Synchronization strategy shapes the model's
design."

The existing architecture has: reactor writes to the Context model, scheduler
reads it, Space manager writes TTBR. One reactor per core means N concurrent
writers.

## The spectrum

Five approaches exist in the wild (research/smp.md §1). The two extremes:

**Full Barrelfish.** N independent kernel instances. No shared state. Cross-core
coordination in userspace. Zero contention. But the complexity gets pushed above
the kernel|userspace interface, and Barrelfish's approach requires userspace
monitors to solve distributed consensus for capability revocation.

**Big Kernel Lock.** One core in the kernel at a time. seL4 does this. Simple,
correct. 23% overhead on ARM from the lock primitive alone (not contention — the
barrier instructions themselves). Fine- grained locking is worse: >70% on ARM.

## Where we landed

Neither extreme. The architecture already implies a natural split:

**The hot path is per-core.** Exception → reactor → update model → scheduler
pick → resume. This happens thousands of times per second. If this path touches
no shared state, there's zero synchronization cost per context switch.

**The cold path crosses cores.** Context migration, cross-core IPC delivery, TLB
shootdown, capability operations. These happen orders of magnitude less
frequently.

This is the hybrid model (research/smp.md §1, "per-core hot path, shared cold
path"). Linux, Zircon, and QNX all land here eventually.

## Shared memory + IPI as the coordination mechanism

The kernel is purely reactive — no kernel thread to poll a mailbox. The only way
to wake a reactor on another core is an IPI (SGI on ARM64). The pattern:

1. Core 0 writes request to per-core mailbox in shared memory
2. Core 0 sends SGI to core 1
3. Core 1 takes IRQ exception, reactor fires
4. Core 1 processes request, writes result
5. Optionally IPIs back

This looks async but fires immediately (~1–2us round trip on ARM64). It's closer
to RPC with interrupt delivery.

The "Wasted Cores" paper (Lozi et al. 2016) is the strongest argument for this
approach: cores sitting idle while other cores were overloaded cost 13–23%
throughput and up to 138x degradation. The cost of NOT sending an IPI dwarfs the
cost of sending one.

## Per-core schedulers

A key insight from this exploration: if each core has its own scheduler, each
core can run a different scheduling algorithm.

- A big core runs CFS-like throughput scheduling
- A LITTLE core runs simple fixed-priority for efficiency
- A core dedicated to real-time Contexts runs deadline scheduling
- Round-robin on one core, CFS on another — viable

This maps to the existing architecture: the scheduler is already a "swappable
leaf node" (spec.md). Per-core makes it swappable per- core.

**Implication for the Context model:** if a Context migrates between cores with
different schedulers, its scheduling properties must be generic — interpretable
by any algorithm. Algorithm-specific state (CFS virtual runtime, deadline
parameters) lives in the per-core scheduler, not in the Context. The Context
carries abstract hints: priority level, CPU-bound vs. IO-bound, optional
deadline. Each scheduler interprets what it understands.

Some information loss on migration is acceptable. A CFS vruntime doesn't
transfer to round-robin, and that's fine — the target scheduler initializes from
the abstract hints.

**No prior art at this exact point.** No surveyed system cleanly separates
per-core scheduler algorithms as a first-class feature. This is a novel
direction.

## The Barrelfish parallel

The architecture derived in journals 001–004 resembles a single-core Barrelfish
CPU driver:

| This kernel             | Barrelfish          |
| ----------------------- | ------------------- |
| Reactor (the spine)     | CPU driver          |
| Context model           | Per-core state      |
| Scheduler `pick()`      | Per-core scheduler  |
| "Kernel is a leaf node" | CPU driver is small |
| Capability-based naming | Capability-based    |
| Small messages + shmem  | UMP + shmem         |

The divergence: Barrelfish pushes cross-core coordination into userspace
(monitors). We keep it in-kernel. The motivation: we don't want the complexity
of distributed consensus above the kernel| userspace interface. On small
cache-coherent ARM SoCs (4–8 cores), shared memory + IPI is simpler and the
contention Barrelfish avoids may not exist.

## What crosses cores

Enumerated the operations that need coordination, roughly by frequency:

1. **Context migration** — move from one run queue to another. The invariant: a
   Context is on exactly one run queue, or "in flight."
2. **Cross-core IPC delivery** — post message + IPI target core.
3. **TLB shootdown** — inherently synchronous. IPI + wait for ack.
4. **Capability operations** — depends on whether caps are shared or per-core
   (still open).

The migration protocol is the interesting one. It bridges per-core and shared:
remove from source queue → write to shared location → IPI target → target picks
up.

## Status

**Tentatively accepted:**

- Hybrid model: per-core hot path, shared cold path
- Shared memory + IPI for coordination
- Per-core schedulers with potentially different algorithms
- Generic scheduling properties in the Context model

**Open sub-questions:**

- What are the abstract scheduling properties? Priority, CPU-bound/ IO-bound,
  deadline — what else? What's the minimum?
- Migration protocol details. Who initiates? What about in-flight messages?
- Capability table: shared with locking, or per-core with replication?
- Multicore bringup under Apple Hypervisor.framework — practical testing
  question
- Core parking / power management: idle core → WFI, woken by IPI
- Thundering-herd prevention: TLB shootdown batching/deferral
